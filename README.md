# Crashproof

A deterministic simulation harness that tests whether the runtime around an agent keeps money-moving actions (return labels, refunds) safe when the systems around it fail. The agent in these runs is scripted, not a language model.

Everything below is a simulation. See Limitations.

A seed fixes one simulated order, return, customer behaviour and fault schedule. Runtimes: naive runs what the agent proposes; keyed adds idempotency keys; hardened adds a ledger, reconciliation, a policy engine with human escalation and a scan timeout. Invariants (docs/INVARIANTS.md): I1 at most one refund per return; I2 total refunded at most the amount paid; I3 refund only after the return scan and only for an eligible order; I4 refund above the cap only with human approval; I5 at most one return label; I6 every confirmed effect has a policy decision (hardened only); I7 no workflow still open 72 virtual hours after activity stops; I8 refunds and ledger entries match one to one (hardened only); I9 the same seed gives the same trace hash.

## What this shows

- The same simulated return requests and the same injected faults are run against three runtimes: naive (executes what the agent proposes), keyed (naive plus idempotency keys) and hardened (keys, a ledger, reconciliation, a policy engine with human escalation, and a scan timeout).
- Hardened shows zero violations of nine safety invariants across the measured seeds.
- Five deliberately broken versions of hardened (key handling removed, key made attempt-dependent, refund cap not enforced, fraud check disabled, scan timeout removed) each produced invariant violations in 300-seed runs; the counts are in docs/DECISIONS.md and the patches are not in the repository.
- Idempotency keys alone remove duplicate refunds in the measured runs (keyed shows no I1 or I2 violations), but not duplicate labels on a provider that ignores keys (I5, carrier B), and they do nothing about policy or liveness failures (the simulated refund service always supports keys).
- Every measured seed replays to an identical trace hash, so any failure can be reproduced from its seed.

## Quick start

Required: Python 3.12 and make.

```
make setup
make test
make eval SEEDS=1000 RUNTIMES=naive,keyed,hardened
make report
make replay SEED=1 RUNTIME=naive
```

This reproduces the table above; SEEDS=200 is a faster smoke run. Some tests skip until an eval has produced results/summary.json.

To refresh the results block above after an eval, run `make readme`.

To inspect a replay, open viewer/index.html in a browser and choose the file results/replay/seed-1-naive.jsonl. The viewer shows the SHA-256 of the file, which equals the hash printed by make replay. If your browser shows "SHA-256 unavailable" for a local file, serve the folder with python -m http.server and open localhost port 8000 in your browser, then go to the viewer folder.

## How it works

- A single-threaded discrete-event scheduler drives virtual time; there is no real clock, thread or network.
- Faults are seeded, and each fault decision depends only on the seed and the logical attempt, so every runtime faces the same fault for the same attempt.
- Each seed is one workflow: one order, one return.
- The world (store, three fictional carriers, refund service, event bus) survives simulated crashes; runtime objects are rebuilt, hardened from its ledger.
- The invariants read world records, the trace order, the approvals log and the ledger; I7 for naive and keyed reads the runtime's own terminal flag.
- Details: docs/ARCHITECTURE.md and docs/INVARIANTS.md.

## Limitations

- This is a simulation only. The carriers are fictional and their failure modes encode the author's assumptions. The results say nothing about real carriers or payment systems.
- The agent in the runs is a deterministic scripted agent, not a language model. No LLM was evaluated and the results are not a measure of any model.
- Faults F4, F6, F7 and F8 (out-of-order delivery, rate limits, provider error schemas, long delays) were specified but not implemented. Only timeouts before and after the effect, duplicated webhooks and crashes after an effect are injected.
- The fault probabilities and scenario mix were fixed before the final evaluation and are arbitrary. Changing them changes the counts.
- The keyed runtime's I3, I4 and I7 failures are expected because it has no policy engine or timeout. The comparison measures what each design includes, not how each design would do if given the same components.
- Hardened's liveness depends on the scan timeout: removing it left 34 of 300 seeds open. Its end-of-run reconcile is not exercised: removing it changed no measured seed.
- Policy rule P3 (refund only after the return scan) denies in 86 seeds but is not terminal; P1 (refund within what was paid for the returned lines) and P5 (one label per workflow) never deny in the measured seeds. P1 and P5 are covered only by unit tests.
- I7 for naive and keyed is a runtime self-report, because those runtimes have no ledger.
- The 1,000 seeds are one deterministic sample of the scenario mix, not a statistical estimate; the counts have no confidence interval.
- After a simulated crash, a rebuilt naive or keyed runtime has no memory of earlier effects or of webhooks it already received; this follows from their having no ledger and is part of naive's and keyed's weakness.
- The simulated refund service always supports idempotency keys and lookup by key; a refund provider without keys was not modelled.
- Crashes are injected only after an effect is applied, and execution is single-threaded; a crash between recording intent and calling the provider, and truly concurrent workers, are not modelled.
- This is not a new idea; see the related-work section in docs/DESIGN.md.
